# 合约号码维护

## 1. 背景

当前“资产管理 → 合约号码维护”用于查询和维护合约号码/合约机资产。原页面基于通用台账组件，字段、查询、编辑边界和合约号码业务规则没有完整落地，且历史说明中混有目标规则和旧代码现状，存在字段口径冲突。

本次改造将合约号码维护收敛为独立业务页面，统一列表、查询、卡片、单条编辑、批量修改、导出和操作历史规则，并以当前确认口径作为最终规则。

## 2. 改造总结

1. 页面固定查询资产大类 `34` 的合约号码/合约机资产。
2. 页面不提供新增、删除入口；合约号码资产由正式业务流程产生。
3. 标签号为蓝色链接，点击打开合约号码卡片。
4. 查看态卡片保留“详细信息 / 合约号码操作历史”两个页签；编辑态只展示“详细信息”，不展示操作历史页签。
5. 卡片详细信息取消业务分组，20 个字段统一使用 3 列 `DetailGrid` 平铺展示。
6. 列表使用详情字段的业务子集，并保留选择框和最右侧固定“操作”列。
7. 列表单条编辑入口固定为右侧“编辑”文字链接，不带图标；顶部不再提供单条编辑按钮。
8. 单条编辑使用接口字段白名单，页面不可编辑字段不得通过接口绕过。
9. 合约号码说明、套餐内容为只读字段。
10. 报废原因、报废日期、领用日期为可编辑字段。
11. 号码状态与仓库强关联：状态包含“在用”时仓库必须为空；其他状态必须选择有效仓库。
12. 报废状态必须同时维护报废日期和报废原因；非报废状态不得残留报废字段。
13. 责任人变化后，姓名、部门、子公司、员工职级、身份证号码根据人员主数据重新派生。
14. 申请类型固定为业务申请 / 个人申请 / 管理者配送，本页面只读；申请单号同样只读。
15. 批量修改继续沿用既有 11 列历史模板，空白表示保留原值；与卡片 20 字段边界独立。
16. 实际发生变化时更新最后修改时间并生成来源为“合约号码台账维护”的事务；无变化不生成无效历史。
17. 查询选择类控件统一使用显式清空能力，不提供“双击清空”等隐藏交互。
18. 编辑态点击“取消”返回当前合约号码卡片查看态，不关闭卡片返回列表。
19. 编辑态内打开公司、责任人等选择弹窗时，选择弹窗必须显示在当前编辑弹窗最上层。

## 3. 通用规则

### 3.1 数据范围

1. 固定查询资产大类 `34`。
2. 查询结果同时满足当前账号数据权限和页面查询条件。
3. 已报废数据继续保留在台账中，可查询、查看详情和历史。
4. 页面不提供新增、删除入口。

### 3.2 权限

1. 没有查看权限的用户不能查看合约号码台账数据。
2. 没有编辑权限的用户不展示右侧“编辑”和“批量修改”入口。
3. 有编辑权限的用户也只能修改本 PRD 明确的单条或批量白名单字段。
4. 页面控件限制与保存接口字段白名单必须同时生效，不能仅依赖前端禁用状态。
5. 导出结果必须同时满足账号数据权限和当前查询条件。

### 3.3 空值展示

1. 列表、卡片、操作历史的普通空值统一展示为 `-`。
2. 编辑控件空值保持为空，不使用 `-` 作为提交值。
3. 单条编辑按字段本身规则处理空值。
4. 批量模板空白单元格表示保留原值。
5. 因当前状态而“不适用 / 不允许维护”的字段，在编辑态直接按只读文本展示 `-`，不使用 disabled 输入框、下拉框或日期控件伪装成可编辑字段。

### 3.4 排序与分页

1. 首次进入按“最后修改时间倒序 → 标签号升序”。
2. 支持业务列手动排序。
3. 翻页后不保留上一页勾选记录。
4. 最右侧“操作”列固定冻结，横向滚动时始终可见。

### 4.5 单条编辑

列表每行最右侧固定“操作”列展示纯文字链接 `编辑`。

点击后直接打开当前记录编辑态，不依赖复选框。复选框继续用于批量修改及勾选导出。

编辑态只展示“详细信息”，不显示操作历史页签。

编辑态底部操作：

1. `保存`：按本文校验规则保存，成功后继续停留当前编辑态并刷新最新数据。
2. `取消`：放弃本次未保存修改，返回当前记录的卡片查看态，并切回“详细信息”页签；不得直接关闭卡片返回列表。
3. 编辑态内打开公司、责任人等选择弹窗时，选择弹窗应覆盖在当前编辑弹窗之上；关闭或确认选择后仍回到原编辑弹窗。

#### 4.5.2 只读字段

以下卡片字段不得通过单条编辑接口直接修改：

1. 标签号。
2. 资产小类。
3. 合约号码说明。
4. 套餐内容。
5. 数量。
6. 部门。
7. 员工职级。
8. 申请类型。
9. 申请单号。

其中部门、员工职级为责任人派生字段；修改责任人后由系统根据人员主数据刷新，但用户不能独立编辑。

除卡片字段外，备注、领用原因、领用说明、副卡、维修记录、子公司、身份证号码等历史字段也不得借单条编辑接口绕过白名单修改。

### 4.6 合约号码校验

合约号码按现有业务规则校验为 11 位手机号，支持 13、14、15、17、18 号段。不满足规则时阻止保存。

### 4.7 责任人及派生字段

1. 责任人选择器查询有效员工。
2. 选择责任人后，姓名、部门、子公司、员工职级、身份证号码重新从人员主数据获取。
3. 页面提交的派生文本值不作为可信保存值。
4. 卡片只展示责任人、部门、员工职级；子公司、身份证号码可作为后台派生数据保存，但不进入卡片字段集合。
5. 非 `SOHU` 开头普通员工没有部门时不允许保存，并提示：`该员工对应的部门为空，请联系管理员添加`。
6. `SOHU` 开头虚拟用户继续走既有特殊逻辑。

### 4.8 状态与仓库

1. 号码状态名称包含“在用”时，仓库必须为空。
2. 非“在用”状态必须选择有效仓库。
3. 状态或仓库任一变更后保存前重新校验组合关系。
4. 不符合规则时提示：`仓库和状态不匹配。`
5. 当前原型有效仓库为 `I10086.集团合约机库`。
6. 编辑态状态为“在用”时，仓库按不适用只读值 `-` 展示，不显示 disabled 下拉框。

### 4.9 报废字段

1. 报废原因、报废日期均可在单条编辑页维护。
2. 报废状态下，报废日期必填且必须为合法日期。
3. 报废状态下，报废原因必填。
4. 非报废状态下，报废日期和报废原因必须为空。
5. 状态切换回非报废时页面自动清空报废字段。
6. 非报废状态编辑态中，报废原因、报废日期按不适用只读值 `-` 展示，不显示 disabled 输入框或日期控件。

### 4.10 领用日期

1. 领用日期为单条可编辑字段。
2. 可为空。
3. 有值时必须为合法 `yyyy-MM-dd` 日期。
4. 保存接口必须执行同样的日期合法性校验，不能只依赖 DatePicker。

### 4.11 申请类型与申请单号

1. 申请类型由上游流程生成，本页面只读。
2. 枚举固定为：业务申请、个人申请、管理者配送。
3. 申请单号同样由上游流程生成，本页面只读。

### 4.12 合约号码操作历史

1. 仅查看态卡片展示“合约号码操作历史”页签，编辑态不展示。
2. 根据标签号查询当前合约号码事务。
3. 按操作日期从早到晚展示。
4. 相邻事务发生变化的主要业务字段使用黄色背景标识。
5. 单条保存未发生实际变化时不生成事务。
6. 本页面人工修改事务来源明确为 `合约号码台账维护`。

## 5. 校验

### 5.1 单条保存

| 校验项 | 规则 |
| --- | --- |
| 使用公司 | 必填且必须有效 |
| 责任人 | 必填且必须有效 |
| 责任人部门 | 非 SOHU 普通员工必须存在部门 |
| 合约号码 | 11 位手机号；13/14/15/17/18 开头 |
| 合约期限 | 日期合法；开始日期不得晚于结束日期 |
| 金额 | 最多 8 位整数 + 2 位小数；不得小于 0 |
| 号码状态 | 必须有效 |
| 状态 / 仓库 | 在用 → 仓库为空；非在用 → 有有效仓库 |
| 报废日期 | 报废状态必填且有效；非报废为空 |
| 报废原因 | 报废状态必填；非报废为空 |
| 领用日期 | 可为空；有值必须为合法日期 |
| 合约号码说明 | 只读，不得提交修改 |
| 套餐内容 | 只读，不得提交修改 |
| 字段白名单 | 页面和保存接口同时限制 |

### 5.2 保存结果

1. 保存成功提示 `保存成功！`。
2. 保存成功后停留当前编辑页，并用保存后的最新数据刷新页面。
3. 保存失败保留用户输入，不产生半条历史。
4. 未发生实际变化时提示 `合约号码信息未发生变化`，不更新最后修改时间，不生成事务。
5. 最后修改时间只能由系统生成，不接受客户端伪造。
6. 编辑态点击“取消”不触发保存，返回当前记录查看态。

## 6. 批量修改

### 6.1 模板字段

批量修改继续沿用既有 11 列模板：

| 顺序 | 字段 | 空白含义 |
| ---: | --- | --- |
| 1 | 标签号 | 必填，用于定位既有资产 |
| 2 | 责任人工号 | 保留原值 |
| 3 | 身份证号码 | 保留原值 |
| 4 | 资产状态 | 保留原值 |
| 5 | IMEI/电话号码 | 保留原值 |
| 6 | 金额 | 保留原值 |
| 7 | 仓库 | 保留原值 |
| 8 | 领用原因 | 保留原值 |
| 9 | 副卡 | 保留原值 |
| 10 | 备注 | 保留原值 |
| 11 | 维修记录 | 保留原值 |

卡片中未展示的历史字段仍可按既有批量接口规则处理，但不得因此重新出现在单条卡片或单条编辑白名单中。

### 6.2 文件及逐行校验

1. 文件必须符合固定模板、表头、列顺序和模板版本。
2. 标签号不能为空且必须存在。
3. 标签对应资产必须属于资产大类 `34`。
4. 同一文件标签号不得重复。
5. 责任人工号填写时必须存在并属于 MMP 管理范围。
6. 资产状态必须存在。
7. 金额必须能转换为数字。
8. 仓库填写时必须存在。
9. 全部行校验后一次性返回已识别错误，不只返回第一条。

校验失败至少展示：行号、标签号、失败原因。

### 6.3 保存策略

1. 全部数据先校验，再进入保存。
2. 任一行校验失败，整份文件不保存。
3. 空白单元格表示保留原值。
4. 正式保存前按标签号重新读取最新资产，避免覆盖导入期间的其他更新。
5. 实际发生变化的记录分别生成修改事务。
6. 原型仅演示“上传 → 校验 → 错误明细 → 保存”流程，不承担真实 Excel 解析。

## 7. 导出

1. 勾选记录时只导出勾选且有权限的数据。
2. 未勾选时导出当前查询条件下全部结果，不只当前页。
3. 导出叠加当前账号数据权限。
4. 导出继续覆盖合约号码台账既有字段，不受列表精简和卡片 20 字段限制。

## 8. 后续操作及补充说明

### 8.1 保存边界

1. 合约号码保存逻辑使用独立 Service，避免与普通资产、耗材维护逻辑互相污染。
2. 历史兼容入口必须转发到同一专用保存逻辑，不能保留可绕过白名单的旧通用 patch 入口。
3. 公司编码、责任人姓名、部门、子公司、员工职级、身份证号码等派生值必须由系统重新获取。
4. 合约号码说明、套餐内容虽然展示在卡片中，但不属于单条维护字段。
5. 报废原因、报废日期、领用日期属于当前单条维护字段。

### 8.2 原型边界

当前原型不具备真实登录权限上下文、真实 Excel 解析和正式后端主数据接口；这些能力由正式研发按本 PRD 接入，原型不伪造“已实现”。
