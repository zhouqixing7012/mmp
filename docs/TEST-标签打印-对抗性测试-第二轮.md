# 标签打印对抗性测试（第二轮）

## 1. 测试范围

本轮在第一轮 B01～B25 回归用例基础上继续扩大攻击范围，重点检查：

- 流水跨年、跨规则和跨页面状态；
- 标签号全局唯一性；
- 批次、标签明细、打印历史三者数据一致性；
- 重复点击、重复回调和幂等；
- 历史累计打印次数与新详细日志的衔接；
- PRD 在第一轮收口过程中是否遗漏原始业务规则。

本轮规则已明确调整：**部件标签按保存的标签类型识别，不再按标签号字符串判断。**

## 3. 第二轮新增发现

| 编号 | 优先级 | 攻击场景 | 结果 / 风险 | 建议处理 |
| --- | --- | --- | --- | --- |
| C01 | P0 | 常规规则选择一个尚不存在当年规则的新年份 | 当前原型对应 key 不存在时直接取 0，与 PRD“跨年续号、不清零”冲突；对于超过15位会去掉年份的常规标签还可能直接生成跨年重复标签 | 当年规则不存在时读取最近上一年规则 CurrentValue；正式服务端仍按规则表事务处理 |
| C02 | P0 | 待生成标签号与资产/耗材台账已有标签相同，但该标签尚未进入标签清单 | 当前 `existingTags` 只来自标签清单，会漏掉台账已有标签 | 标签唯一性按全局标签空间校验：标签清单 + 已有资产卡片 + 耗材卡片；数据库保持标签号唯一约束 |
| C03 | P0 | 极快连续点击“生成标签” | `generating` 仅为 React state，同一事件刷新周期仍存在二次进入窗口 | 原型增加同步锁；正式后端继续使用生成请求幂等键 |
| C04 | P0 | 批次写入失败，但流水已执行 `reserveSequence` | 当前生成逻辑先推进流水，再调用批次/标签写入；后续写入失败时可能出现“无标签但流水跳号” | 原型先确认批次/标签写入再推进流水；正式批次、标签、流水必须同一事务提交/回滚 |
| C05 | P0 | 特殊规则-备件依次选择 CPU、Card、HD、ME、SP | 第一轮修复把备件按类型拆成不同流水，但原始 PRD明确“所有备件确定一组流水号，不清零” | 改回所有备件共用一个 `CurrentValue`；备件类型只影响标签前缀 |
| C06 | P1 | 新年份规则不存在时生成常规标签 | 除 C01 外，当前页面“当前最大序号”也会显示 00000，容易让用户误判流水从头开始 | 页面展示继承后的最新 CurrentValue，并在正式后端生成前再次读取 |
| C07 | P1 | 查看初始化批次的标签清单 | 当前批次 `labelCount` 与实际 Mock 标签明细条数不一致；例如批次显示3/4条，但标签清单只有1/2条 | Mock 批次、标签明细和日志数据保持一致；批次标签数必须等于标签明细数 |
| C08 | P1 | 点击“是否已打印=是”的历史批次查看打印历史 | 部分初始化批次标记已打印但没有对应日志，产生“已打印但无历史”状态 | Mock 补齐至少一条成功日志；正式系统批次已打印必须由成功日志推导 |
| C09 | P1 | 高耗规则选择完整业务分类 | 原型缺少 `家电（ES权限）`，且办公设备/家电子类归类不完整 | 按原始 PRD恢复完整高耗大类/小类映射 |
| C10 | P1 | 核对资产主列表 `PRINTED_COUNT` 与详细日志 | 主列表补打本身不写详细日志，不能要求日志合计等于主列表累计次数 | 两条链路分别统计；主列表只维护 `PRINTED_COUNT`，预打印/接收单按标签明细和日志核对 |
| C11 | P1 | Brother成功回调/网络重试重复提交同一打印结果 | 生成接口已有幂等要求，但打印结果确认接口未明确幂等，重复回调可能重复累计次数 | 每次打印动作生成唯一 `printTaskId`，打印结果确认接口按任务幂等，成功任务重复确认不得再次累计 |
| C12 | P1 | 极快连续点击“确认打印” | 当前 `confirmPrint` 无处理中锁，同一刷新周期存在重复累计风险 | 原型增加打印提交同步锁/按钮 loading；正式后端由 `printTaskId` 幂等兜底 |
| C13 | P1 | 打印失败后查看详细历史 | 技术日志可保留失败原因，但业务打印历史列表不展示该技术排障字段 | 失败原因保留后台排障使用，不加入当前业务历史列表 |
| C14 | P1 | 核对预打印与资产接收标签流水 | 第一轮精简后的 PRD没有再次强调“预打印与资产接收共用同一标签生成服务/流水” | PRD补回跨模块共享规则，避免两条链路各自维护 CurrentValue |
| C15 | P1 | 资产/耗材卡片信息更新后查看标签打印列表 | 第一轮精简后的 PRD弱化了“标签打印列表动态展示最新卡片信息”的原始规则 | PRD补回：按标签号动态获取资产/耗材最新卡片字段，台账变更后同步展示 |

## 4. 需求回归中确认的原始规则

本轮重新对照第一版需求，以下规则必须继续保留，不能被第一轮重构误删：

1. **预打印与资产接收生成标签使用同一套标签生成规则和流水服务，跨年不清零。**
2. **特殊规则-备件：所有备件共用一组流水号，不清零；CPU / Card / HD / ME / SP 只决定标签前缀。**
3. 高耗规则完整分类至少包含：
   - 电脑配件：内存、内置硬盘、板卡；
   - 电脑外设：移动硬盘、移动光驱；
   - 办公设备：会议白板、验钞机、考勤机、碎纸机；
   - 家电（ES权限）：微波炉、电扇|空调扇、饮水机、咖啡机、电暖器、机顶盒；
   - 合约机：合约手机、合约电话卡。
4. 标签打印列表动态获取资产卡片、耗材卡片最新信息；台账信息变化后按资产/耗材标签号同步展示最新字段。
5. 预打印生成标签和资产接收生成标签均进入统一标签清单和批次追溯体系。
6. 资产接收完成相关标签标识后，标签打印模块应出现对应可追溯记录。
7. 标签生成时间以实际执行“生成标签”操作时刻为准。

## 5. 正式实现新增必测项

除第一轮列出的真实硬件/权限/并发测试外，第二轮新增：

1. 新年份规则不存在时，从上一年度未用完流水继续编号；
2. 去年份后的超长常规标签跨年仍不得重复；
3. 备件不同类型并发生成时仍共享同一 CurrentValue；
4. 同一打印任务成功回调重复2次，只累计1次；
5. 打印结果接口超时重试，不重复累计次数；
6. 批次/标签写入失败时流水必须回滚；
7. 流水更新失败时批次/标签必须回滚；
8. 台账已有标签但标签清单缺少对应历史记录时，预打印仍必须识别标签号冲突；
9. 上线前历史累计次数按基线迁移，不伪造打印时间、IP和打印人。

## 6. 当前结论

第二轮证明第一轮主要交互修复方向正确，但又发现了几项**规则级问题**，其中 C01～C05 必须在继续下一轮前收口，否则仍存在跨年重复标签、全局标签冲突、重复提交或备件流水错误的风险。

部件标签识别规则已纳入本轮 PRD 整改；后续代码同步必须使用标签类型字段选择模板。
