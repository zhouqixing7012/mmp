# 实现约束与回归检查

本文记录原型实现中的固定技术约束，用于避免出现“提交成功、构建成功，但业务页面实际未生效”的情况。

## 1. 结构性 UI 变更必须修改源码结构

以下变化属于结构性 UI 变化：

- 删除或新增表格列；
- 隐藏或新增页签；
- 字段显隐；
- 编辑态与查看态结构差异；
- 查询条件合并、拆分或改成范围控件；
- 操作按钮增删；
- 业务字段从页面移除。

这些变化必须直接修改对应页面的 JSX、`columns`、`items` 或条件渲染逻辑。

禁止仅通过以下方式模拟结构变化：

- 全局 CSS `:has()`；
- `nth-child` 定位表格列；
- 根据 DOM 顺序隐藏列或页签；
- 依赖全局样式猜测 Ant Design 内部 DOM；
- 在公共组件中通过字段名称自动识别并偷偷合并业务查询条件。

CSS 只负责视觉表现，不负责业务结构。

## 2. 本次问题原因

2026-09-16 标签打印及维护菜单 UI 调整中，部分需求最初通过全局 CSS 和 QueryBar 自动识别实现，例如：

- 标签批次列表隐藏“来源”；
- 标签清单隐藏“标签批次”；
- 打印历史隐藏技术字段；
- 单一编辑页签隐藏；
- “打印时间从 / 打印时间至”自动合并。

这些实现依赖 Ant Design 实际 DOM 层级、列顺序和 CSS 选择器命中情况。GitHub 提交和 Vercel 构建均可能成功，但页面结构未必真正发生变化，因此出现“部署成功但页面未生效”。

最终修复方式是：

- 直接从 `columns` 删除对应列；
- 编辑态直接渲染详情内容，不创建单一 Tabs；
- 打印时间直接使用 `RangePicker`；
- 业务字段与内部日志字段在页面数据结构和展示层明确分离。

## 3. 验证规则

结构性 UI 变更完成后，不能只检查：

- commit 已生成；
- Vercel 状态 success；
- CSS 中存在对应规则。

必须至少再检查一次最终分支源码：

1. 要删除的表格列是否已经不在 `columns` 中；
2. 不应展示的页签是否已经不参与 JSX 渲染；
3. 查询范围是否由目标页面直接使用范围控件；
4. 业务 UI 是否仍引用内部日志字段；
5. 最终 `main` HEAD 是否包含目标源码变更；
6. Vercel 构建成功后再进行页面验证。

## 4. QueryBar 固定布局口径

查询区默认保持三列：

- 每行最多 3 个查询条件；
- 默认标签宽度 88px，右对齐；
- 字段列之间沿用 16px gutter；
- 查询条件区域与右侧查询操作区保持 24px 间距；
- 查询、重置等操作继续独立位于右侧，不挤入第三列；
- 范围查询由业务页面显式使用 `RangePicker` 等范围控件，不由 QueryBar 根据字段名称自动改写。

如个别页面确有超长字段名，可通过 `labelWidth` 显式覆盖，但不得因此修改所有页面。
