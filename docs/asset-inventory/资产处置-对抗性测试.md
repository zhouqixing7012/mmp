# 资产处置 PRD 对抗性测试（2026-09-28）

## 范围与证据

- 目标：`docs/PRD-资产管理-资产处置.md`；写作规则：`docs/PRD-撰写偏好与规范.md`，以及用户在本轮确认的“没有处理中，办理过程也属于审批中”。
- 原始需求：`docs/source/机房资产报废(1).docx`、`docs/source/非机房资产报废(1).docx` 中的处置段落。原始文档是历史依据，不覆盖较新的明确业务确认。
- 原型及演示数据：`ScrapPrototypeModule.jsx`、`ScrapPrototypeEditor.jsx`、`ScrapPrototypeList.jsx`、`scrapPrototypeData.js`、`scrapPrototypeWorkflow.js`、`scrapPrototypeApproval.js`、`scrapPrototypeService.js`，以及对应回归测试。
- 静态源码只能证明当前原型路径；不能证明生产身份、资产台账、真实文件保存、通知渠道或业务执行已经实现。

## 逐项攻击与处理

| 场景与攻击方式 | 原始文档或已确认需求 | 原型与原 PRD 证据 | 本轮结论与处置 |
| --- | --- | --- | --- |
| 用旧状态打开机房协办或办公 ES 办理单，再刷新 | 用户确认处置单没有“处理中”，节点进行中都为“审批中” | 原 PRD 列有“办理中”“待 ES 专员处理”；原型筛选、Mock 与自动创建曾写“处理中” | PRD 改为草稿、审批中、已驳回、已完成；原型生成与列表统一，旧浏览器记录原位迁移状态，保留原节点与历史，测试覆盖 |
| 用软件、丢失或调账资产尝试创建处置单 | 最新确认仅 17.SOFTWARE、丢失、调账不进待处置池且不生成单；不存在“是否处置”字段 | 原型历史上曾依赖处置配置字段和机房数据清洗结果 | 已改为直接按资产大类、报废类型、报废方式判断；其他资产均进入处置 |
| 用两个板块、同一个公司的资产加入同单，再换公司 | 已确认单据公司唯一，但允许多个板块 | 处置候选按公司过滤；原 PRD 只写“财务公司+板块隔离”，没写同单板块规则 | PRD 明确各资产保留板块、同公司可多板块；公司改变必须先移除明细；原型对处置权限的真实身份/板块过滤尚无可靠证据 |
| 填三家供应商及逐项报价，清空其中一个再提交 | 最新确认单头三家供应商名称，明细三家报价且逐列求和；不能再出现额外报价区块 | 原型单头输入、逐项报价及编辑合计具备；原始非机房文档曾列五家回收商 | PRD 维持三家名称及金额，Excel 列名更正为“回收商一/二/三报价”；历史五家数据迁移方式未定义 |
| 把同 City + 大类中相同金额的两件资产放入审批摘要 | 用户确认办公单既逐项列报价，也按回收商维度展示整单合计 | 原型曾按列去重连接，两件相同报价只剩一个金额 | 已移除去重，组内逐项展示且重复金额照列；审批与编辑均按每家回收商汇总整单报价 |
| 完成账面报废后自动建立机房处置单，查看三家供应商名称 | 用户确认机房自动单无三家回收商信息，也不需要报价 | 原型给机房单补三家供应商和报价 Mock，表头、审批摘要与导出沿用办公单 | 机房单头、明细、摘要、导出及 Mock 均移除三家回收商字段；仅办公手工单填写和汇总报价 |
| 北京、非北京机房分别走协办与清洗 | 最新确认机房资产均需处置，数据清洗只决定是否增加清洗协办 | 旧规则曾把非北京且数据清洗=否误判为无需处置 | 已改为机房账面报废完成后均自动生成处置单；非北京且无需清洗时不增加清洗协办 |
| 当前处理人未上传新附件却点协办完成 | PRD 要求北京到款凭证、交接签字表及适用的数据清洗报告；机房处置全流程只使用单头附件 | 原型已将各协办节点上传统一追加至单头附件，并仅给新文件记录上传节点/时间；推进时校验当前节点至少新增 1 个附件 | 当前原型已具备节点级材料拦截和来源记录；真实文件持久化、上传人身份及下载权限仍需正式环境验证 |
| 在详情页伪造审批意见、从进度弹窗执行操作 | 审批页当前节点可处理；单号详情只读；进度只读 | 原型 `approvalPage` 控制可操作态，进度入口独立 | PRD 分别列入口、操作限制及无权限结果；需以真实身份映射验证最终权限 |
| 刷新当前原型，检验单据、明细、节点和历史 | 当前报废专项已确认不使用 LocalStorage | 原型业务单据仅保存在页面会话内存，刷新后重新加载仓库最新 Mock | 当前行为与最新原型口径一致；生产持久化仍由正式后端实现，不以浏览器原型代替 |
| 试图让旧非机房文档中“处置先于账面报废”“五家供应商”等规则返回新版 PRD | 最新明确账面报废完成后才进入处置，回收商恰为三家 | 原始两份 Word 与现版原型/近期确认冲突 | 最新明确口径优先；历史迁移与存量单据展示未有业务决定，列未定义，不自行选旧规则 |

## 尚需兑现的原型差距

| 差距 | 可复核的路径 | 对正式验收的影响 |
| --- | --- | --- |
| 静态待处置资产池的来源单号不是由已完成账面报废结果逐项校验得到 | `scrapPrototypeData.js` 的 `DISPOSAL_ASSET_POOL`；`scrapPrototypeService.js` 的 `getDisposalCandidates` | 无法证明每件可选演示资产都符合前置账面报废来源；需真实来源对账 |
| 处置单的保存和提交缺少统一的公司、板块、重复占用及来源二次校验 | `ScrapPrototypeModule.jsx` 的 `saveRecord` 与编辑页 `validate` | 正式执行业务不能直接沿用原型的可点击路径 |
| 审批人和各组织授权缺少真实身份映射 | 处置模块原型与本仓库本地演示身份 | 对越权审批、查看、导出不能据此作生产验收 |

以上未实现项记录为现状差异，不写作主 PRD 的实现方案；已确认的目标规则留在正式 PRD 对应章节，未定义事项集中放在第 6 章“当前尚未定义”。

非北京且无需数据清洗的机房资产仍必须生成处置单；由于没有人工协办节点，系统生成后直接完成并保留处置结果。当前原型不使用 LocalStorage，不保留旧浏览器业务快照。
