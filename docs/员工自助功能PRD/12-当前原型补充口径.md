# 当前原型补充口径

> 生效日期：2026-09-04  
> 适用范围：本目录 00～11 的来源 PDF 拆分 PRD，以及 `docs/PRD-EMPLOYEE-ASSET-SELF-SERVICE*.md` 中与当前原型重复描述的部分。

## 1. 文档优先级与使用方式

本目录 00～11 继续保留来源 PDF 原文，用于需求溯源；已经被后续原型明确调整的内容，以本文件和项目当前实现口径为准。

阅读优先级：

1. 用户最近明确确认的业务口径。
2. 当前原型已落地并在本文件记录的补充口径。
3. `docs/PRD-EMPLOYEE-ASSET-SELF-SERVICE*.md` 等当前实现 PRD。
4. 本目录 00～11 的来源 PDF 原始口径。

如果原始 PDF 与当前原型冲突，不直接改写原始段落；在本文件补充覆盖规则，保留可追溯性。

## 2. 通用申请人信息口径

业务页面“申请人信息”的默认身份字段集合和顺序固定为：

1. 申请人
2. 申请日期
3. 公司
4. 办公区
5. 联系电话
6. 邮箱
7. 部门

默认不把板块、成本中心、退库类型、员工状态等作为申请人身份字段展示。

业务原因字段不属于身份字段，例如退库原因、申请原因、更换原因；业务明确需要时继续保留，并优先放在默认 7 字段之后独占完整新行。

### 2.1 公司展示口径

普通业务页面“公司”使用 `编码.公司名`，当前常用演示值为：

`114.新媒体`

`集团 / 媒体 / 视频 / 焦点` 是子公司或组织层级，不作为普通“公司”字段值。只有号码控制等明确展示组织路径的场景，才以这些层级名作为路径起点。

### 2.2 联系电话 Mock 口径

业务页面及用户信息中的“联系电话”Mock 使用座机号格式，例如 `010-56602852`，不使用 11 位手机号或手机号掩码。

合约号码、电话号码等号码资产字段属于业务资源本身，不受此规则影响。

历史演示数据如果通过 `demoStorage` 持久化，读取和写入时会把旧手机号/手机号掩码归一为座机并回写，避免旧 localStorage 继续展示手机号。

## 3. 资产申请、业务审批与统一申请汇总

### 3.1 业务审批

申请人信息公司固定展示为 `114.新媒体`。

“申请资产信息”当前字段：

- 资产说明
- 配置
- 数量
- 申请用途
- 申请原因
- 是否超标

原“详细说明”展示名改为“申请原因”，底层仍使用 `detail`，不改变审批数据结构和流转逻辑。

### 3.2 统一申请汇总-资产审批

审批页继续是可审批页面，底部保留：

- 同意
- 驳回
- 返回

在“超标申请”区域上方提供“导出申请明细”按钮，复用当前 CSV 导出逻辑；审批表仍保持只读。

## 4. ES 前台领用与员工领用确认

详细现行口径同步到 `docs/PRD-EMPLOYEE-ASSET-SELF-SERVICE-PHASE3.md`。

### 4.1 ES 前台领用

申请人身份字段使用默认 7 字段，并额外保留当前仓库作为办理字段；删除成本中心，不展示单据备注。

申请资产信息当前调整：

- 删除“所在仓库”展示，但资产仓库仍参与当前仓库一致性校验。
- 启用日期后展示只读“备注”。
- 地理位置字段统一使用 `city / building / floor`。
- 原“详细说明”在本节点展示为“申请原因”。
- 使用说明为单行输入。

### 4.2 员工领用确认

该页面与资产更换链路中的“员工资产确认”不是同一页面。当前员工领用确认仍展示“使用人 / 部门”，并展示红字确认提示及资产保管职责。

## 5. 耗材领用

耗材领用方案一、方案二的申请人信息：

- “使用人”统一改为“申请人”。
- 删除成本中心。
- 两个方案的地理位置字段统一使用 `city / building / floor`。

当前两个方案均不展示“使用用途”。

方案一“物料编码”和方案二“耗材标签号”均为只读文本，不作为用户输入字段。

## 6. 资产借用

### 6.1 员工名下资产明细

借用配给的“员工名下资产明细”查询条件当前为：

- 资产标签号
- 资产状态
- 资产说明
- 是否锁定

不再提供“物资总类”和“资产用途”。

### 6.2 借用发放

申请人信息继续包含默认身份字段，并保留当前仓库作为办理字段。

“借用资产明细”当前口径：

- 地理位置字段为 `city / building / floor`。
- 资产说明仅展示“品牌.型号”，不展示资产小类前缀。
- 申请人信息和借用资产明细统一使用 `DetailGrid` 三列栅格，保证跨 Card 的标签宽度和列边界对齐；不要在同一组三列详情区混用 Antd `Descriptions`。

### 6.3 员工借用确认

人员字段使用“申请人”，不再写“使用人”。

## 7. 资产更换

### 7.1 资产更换申请

退回资产信息中的资产说明仅展示“品牌.型号”，不展示资产小类前缀。

更换须知当前只保留第一条可见提示。

### 7.2 资产更换办理

更换物资信息、待发放资产信息的地理位置字段统一使用 `city / building / floor`。

申请人旁提供眼睛图标 + 蓝色 link Button“查看名下资产”，打开员工名下资产明细弹窗。

### 7.3 员工资产确认

“使用人”改为“申请人”。

领用确认场景在“确认提示及保管职责”中追加红字保管职责：

> 保管职责：领用人须承担妥善保管物资的责任，除自然损耗外，不得人为损坏或者疏于维护，否则承担相应的赔偿责任。应公司需要，领用人应当配合及时调换或归还借用物资，如延迟甚至拒绝交还公司物资，公司保留采取进一步手段的权利，包括但不限于留置领用人工资、奖金或者其他个人物资。

该保管职责仅在领用确认场景展示，退库确认场景不展示这段领用职责。

## 8. 资产退库

### 8.1 退库审批

申请人信息补齐公司、办公区；删除退库类型；退库原因继续作为业务原因字段保留。

### 8.2 领导退库审批

申请人信息使用默认 7 字段，公司使用 `114.新媒体`；最后单独整行展示退库原因。

### 8.3 资产退库办理

申请人信息使用默认 7 字段，公司使用 `114.新媒体`，最后单独整行展示退库原因。

申请人旁提供“查看名下资产”，弹窗使用资产退库业务数据；查询条件为：

- 资产标签号
- 资产状态
- 资产说明
- 是否锁定

不展示“物资总类 / 资产用途”。

退库资产信息地理位置字段统一使用 `city / building / floor`。

## 9. 合约号码申请、领用与退库

### 9.1 合约号码库管员待办

申请人信息删除板块、成本中心；本轮未要求把该页面“使用人”改名，因此原人员字段名称继续保持当前页面实现。

申请合约号码信息继续按当前最小业务字段展示，不因为底层数据仍有其他属性就补回页面。

### 9.2 合约号码退库办理

申请人信息使用默认 7 字段：申请人 / 申请日期 / 公司 / 办公区 / 联系电话 / 邮箱 / 部门。

删除板块、成本中心，最后单独整行保留退库原因；公司展示为 `114.新媒体`。

## 10. 当前仍未完全收敛的页面

“默认 7 字段”是统一目标，但当前原型中仍存在少数确认页或合约号码审批/配给页尚未补齐全部 7 字段。未被用户明确要求修改的页面不在本轮文档同步中虚构为“已完成”。

后续修改这些页面时，应优先按第 2 节默认口径收敛，并保留业务明确需要的原因字段。

## 11. UI 与原型实现经验

### 11.1 跨 Card 三列对齐

当同一页面多个业务 Card 都是三列详情布局，且需要竖向边界跨 Card 对齐时，统一使用 `DetailGrid + DetailItem`。不要只把其中一个 Card 改成 `DetailGrid`，其他 Card 继续用 Antd `Descriptions`；两套布局算法不同，会造成跨 Card 竖线错位。

### 11.2 只读字段

只读业务字段直接展示文本或状态，不使用 disabled/readOnly 输入框模拟只读；只有真正需要用户编辑的字段才使用 Input、Select 等控件。

### 11.3 整行字段

申请原因、退库原因、备注、配置等需要整行展示时，`span={3}` 必须从完整新行开始。删除前置字段后，普通短字段可以自然补位，但整行字段不要被机械上移到半行之后。

### 11.4 文档同步

原型确认发生以下变化时，需要同步文档：

- 字段增删、改名、顺序和是否整行。
- 业务提示、确认文案、保管职责等固定文案。
- 审批/办理按钮和流转节点。
- 查询条件、弹窗字段、导出能力。
- 会影响后续页面实现的一般 UI 经验。

来源 PDF 文档保留原文，使用本补充口径记录后续覆盖；当前实现 PRD 可以直接修正文档正文和验收项。
