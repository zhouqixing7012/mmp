# 原型标注生成规范

## 目标

原型标注同时满足两件事：

1. **位置准确**：字段规则贴字段、按钮规则贴按钮、Tab 规则贴 Tab、表格列规则贴列头；只有跨多个对象的统一规则才放模块标题。
2. **内容完整**：PRD 中需要研发关注的规则必须有明确去向，不能因为找不到页面元素就静默遗漏，也不能为了“有地方放”而粗暴塞进模块标注。

## 一、先拆 PRD，再做标注

不要直接按 PRD 段落或页面 Card 生成标注。先把 PRD 拆成最小研发规则单元（Requirement Atom）。

每条规则至少记录：

| 字段 | 说明 |
| --- | --- |
| requirementId | 稳定编号，例如 `CN-WH-005` |
| source | PRD 文件 + 章节/表格位置 |
| page | 所属页面 |
| objectType | page / module / field / action / tab / table-column / modal |
| object | 具体对象，如“弃领按钮”“申请原因字段” |
| rule | 研发需要实现/测试的规则 |
| attention | high / normal / low |

同一句 PRD 如果同时描述两个按钮、两个字段或两个不同结果，必须拆成多条规则，不能因为它们写在同一段就合并成一个标注。

## 二、目标粒度优先级

生成标注时按下面顺序找目标：

1. **action** → 具体 Button
2. **field** → 具体 DetailItem / FormItem / QueryItem / 控件
3. **tab** → 具体 Tab
4. **table-column** → 具体表头
5. **modal** → 弹窗内具体字段/按钮，其次弹窗标题/整体
6. **module** → Card / 分组标题
7. **page** → 页面级统一规则

### 硬约束

- `action-rule` 必须绑定 `::button::`。
- `field-rule` 必须绑定字段或具体控件，不能绑定 Card/module。
- `tab-rule` 必须绑定 `::tab::`。
- `table-column-rule` 必须绑定 `::table-column::`。
- 页面存在更细目标时，禁止为了省事回退到模块。

## 三、哪些内容可以合并

只有满足以下条件才允许合并到同一条标注：

- 针对同一个页面对象；
- 触发条件相同；
- 结果属于同一业务分支；
- 合并后不会让研发误以为规则对整个模块都生效。

例如：

- “弃领不生成出库单”“弃领释放号码锁定”“弃领后不能继续正常领用”都属于同一个“弃领”按钮，可以合并为一条按钮标注。
- “领用确认进入员工确认”和“弃领结束流程”虽然同属审批操作区域，但属于两个按钮、两个业务分支，必须拆成两条按钮标注。

## 四、覆盖账本

每个 PRD 模块生成标注时同步维护 Requirement Coverage Ledger。每条研发重点只能处于以下状态之一：

| 状态 | 含义 |
| --- | --- |
| `bound` | 已绑定到准确页面目标 |
| `review` | PRD 与当前页面/最新口径冲突，或页面不存在可靠目标，必须显式待确认 |
| `skip` | 明确不需要单独标注，并记录原因 |

禁止存在“未进入账本”的研发重点。

### review 的典型场景

- PRD 写了字段，但当前页面不存在；
- PRD 默认值与页面代码/后续产品确认口径不一致；
- 规则对象存在，但无法生成稳定语义 target；
- PRD 本身前后矛盾。

这类内容不要擅自改页面，也不要挂到模块标题假装已经处理，应进入 `review`。

## 五、质量检查

代码侧使用 `annotation-quality.js` 做两类检查：

### 1. Granularity Check

检查规则类型和 target 粒度是否匹配。例如：

- `action-rule` → 非 Button target：失败；
- `field-rule` → Card target：失败。

### 2. Coverage Check

检查覆盖账本：

- `bound` 必须存在对应 annotation；
- 可指定 `expectedTargetFragment` 校验具体对象；
- `review` / `skip` 必须写明原因；
- 不能有重复 requirementId。

## 六、Agent 生成流程

后续 Agent 根据仓库 PRD 生成标注时固定执行：

```text
读取 PRD
  ↓
拆 Requirement Atom
  ↓
按页面读取 React 代码 / 可标注目标
  ↓
逐条匹配最细业务对象
  ↓
生成 annotation data
  ↓
生成 coverage ledger
  ↓
Granularity Check
  ↓
Coverage Check
  ↓
仍无法准确定位的进入 review，不自动回退模块
```

## 七、合约号码库管员示例

PRD “库管员待办/领用办理页”中：

- `领用确认`：绑定“领用确认”Button；说明进入员工领用确认页。
- `弃领`：绑定“弃领”Button；说明结束流程、不生成出库单、释放锁定、禁止恢复正常领用。
- `返回`：仅返回上一页，无数据副作用，可在覆盖账本中 `skip`。
- `城市默认北京市`：当前 PRD 与页面实际默认逻辑不一致，进入 `review`，不擅自生成错误字段标注。

这样既不会把两个按钮规则塞到“审批操作”模块标题，也不会因为页面口径不一致而把 PRD 重点直接丢掉。
