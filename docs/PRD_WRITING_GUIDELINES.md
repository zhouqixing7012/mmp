# PRD 写作规范

这是资产系统 PRD 表述、组织和比对方式的唯一维护位置。具体字段、流程、权限和结果由对应正式 PRD 定义。

## 结构

默认按“背景 → 权限 → 通用规则 → 页面字段及交互 → 校验 → 后续操作 / 业务结果 / 补充说明”组织。存在明确前后变化时在背景后补充改造总结；不为套模板拆出没有内容的章节，不单独增加验收标准章节，不使用装饰性分割线。

兄弟模块保持相同一级结构与同类规则命名，但不为统一形式强行增加业务字段。重构前列出原有细节，保证权限、状态、数量占用、字段锁定、校验、异常、下游结果、打印和特殊场景完整保留。

## 规则写法

- 使用业务名称、触发条件、允许操作和结果，写成研发能执行的业务规则。
- 不写“沿用既有规则、按原逻辑、继续使用现有能力”等依赖隐含背景的表述；查不到具体规则时列为未明确，不补造结论。
- 主 PRD 不混入数据库表名、代码字段名、SQL、接口方法、类名、内部任务字段或实现方案。技术证据放技术设计、三方比对或验证记录。
- 用“重复提交只产生一次结果”“任一步失败不产生部分结果”等业务结果表达约束。
- 不写“已完成、当前原型、Mock、文件路径、后端待实现”等项目状态；正式要求与演示说明分别维护。
- 不用“完整、较完整、成熟度高”等评价代替具体规则。
- 同一规则在其所属章节完整定义一次。页面章节写页面表现，校验章节写拦截条件，不整段重复复制。
- 字段表已明确页面范围时，不再罗列没有新增约束的“不展示、不负责、不直接处理”。确实需要系统拦截的限制必须保留。

## 字段、弹窗与操作

| 对象 | 必须写清的内容 |
|---|---|
| 页面字段 | 页面字段 / 业务含义 / 交互规则；必要时说明来源、默认值、必填、只读、枚举、长度与联动 |
| 查询 | 每个字段的匹配方式、多个条件的组合、触发方式、重置和结果行为 |
| 选择弹窗 | 入口、查询条件、结果列、选择规则与回填结果 |
| 按钮 | 展示条件、可用条件、点击结果；区分隐藏和置灰 |
| 流程 | 操作人、进入条件、状态变化、数据结果、失败时的业务表现 |
| 历史与打印 | 入口、数据来源时点、展示内容、排序与相关权限 |

页面名称、字段、按钮、查询和打印历史写在对应页面章节，不另设“页面固定口径”。图标、视觉形式、固定列位置、控件样式和打印组件运行环境归入 UI 或工程规范，只有构成业务约束时才进入 PRD。

工作台需求需要明确职责、待办准入、查询匹配、条件组合、回车触发、0/1/多条结果、办理入口和异常，不套用静态单据类型白名单替代实际办理场景。

固定账号白名单如果已被确认为正式权限，可以写账号和姓名；禁止写入正文的是演示账号，不是所有具体账号。

## 新旧资料和原型同步

1. 原版 PRD 和用户提供的原始资料只读保存，用于历史追溯。
2. 当前原型说明已实现内容，不自动代表目标规则；新版 PRD 承载用户确认的最终业务目标。
3. 比对“原版 PRD / 当前原型 / 新版 PRD”，区分历史规则遗漏、后续改造替代、仅后端规则以及真正待确认的差异。
4. 待确认问题集中成表，写来源、推荐答案和影响；建议没有获得确认前不能作为正式规则执行。
5. 用户确认后同步受影响的新版 PRD 和原型；后端规则无需在前端模拟时保留为研发要求，不用假前端逻辑制造已实现效果。
6. 报废专项按“现状资料 → 新流程 → 新版 PRD → 原型 → 用户精调 → 三方比对 → 差异确认 → 同步收口”推进，已获得确认的阶段不重复审批。
